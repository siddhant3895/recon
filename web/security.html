Security & Data Handling

Recon is currently a working prototype, not a hosted service. This page describes exactly what the software does with data today, and clearly lists the protections it does not yet have.

What Is True Today

Data Location Wherever you run it. Recon is a single-process Python application. It calls no external APIs and stores nothing in any cloud. Data exists only in the memory and disk of the machine running it.
No LLM in the Match Loop None, ever. Parsing and match scoring are deterministic Python code running locally. Documents are never forwarded to third-party AI services.
Demo Data Synthetic. The public demo runs on generated sample data (a seeded generator in the repository). No real bank statements or client ledgers are included.
Decision Audit Trail Append-only. Every accept/reject/unmatch/undo decision writes an immutable audit record (who, what, when, reason). Resetting the demo clears decisions but preserves the audit history.
Exports Built in memory, streamed to you. XLSX/CSV exports are generated in memory and sent directly to your browser; the server does not retain a copy.
Retention Job Included, operator-run. The codebase ships a purge job that deletes raw upload files past a purge_after timestamp and writes an audit event for each outcome (purged / skipped / failed). It is designed to be scheduled by whoever operates the software; it is not wired to a live service yet.

1. How Data Actually Flows

In the current prototype, the only data entered through the web interface is the "shadow month" interest form (firm name, contact details, volume estimates). That submission is held in the running process's memory and written to its in-memory audit log; it is not persisted to a database, not emailed anywhere, and is lost when the process stops. Reconciliation runs are performed via the command line on files you supply, and results are written to your local disk under your control.

2. Raw File Retention & Purge

  • Upload records carry a purge_after timestamp; the purge job removes files whose timestamp has elapsed.
  • Every purge outcome writes an audit event: file purged (with bytes freed), skipped (record unparseable or key escapes the storage root), or failed (file could not be deleted — the record is never falsely marked purged).
  • Records with invalid timestamps or suspicious storage paths are never deleted and never marked purged; they are surfaced so the registry can be repaired.
  • Running the job and its scheduling (e.g. daily) is the operator's responsibility — it is a documented command, not a hosted automation.

3. What We Do NOT Have Yet

Honesty matters more than a reassuring table. The following protections do not exist in this prototype and must be built before any real client data is processed:

  • No authentication or user accounts. The web demo has no login; anyone with access to the port can use it.
  • No multi-tenancy or row-level security. There is a single shared in-memory workspace, not per-firm isolation.
  • No encryption at rest or in transit. The dev server speaks plain HTTP; data on disk is not encrypted by Recon.
  • No cloud residency guarantees. Because nothing is hosted, "Indian data residency" depends entirely on where you run it.
  • No automated incident response. There is no monitoring, alerting, or breach-notification pipeline.
